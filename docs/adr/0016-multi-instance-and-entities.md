# 多实例模型：MVP 单运行实例；实体模型 Distro ≠ Image ≠ Instance ≠ Session

> 标注约定：【产品决策】= 已拍板；【工程假设】= 有证据支撑但属类比/推断；【待验证】= 需后续数据。

1. 【产品决策】MVP **同时最多运行一个 Full Linux 实例**；可存在多个已停止实例；**切换 = 停止当前 + 冷启动目标**。多实例并发**不进 MVP**，作为后续增强由真机内存/功耗数据决定是否解锁（能力矩阵声明）。
2. 【产品决策·领域模型】四个实体**不可合并**：
   - **Distro（发行版）**：DistroManifest 描述的可安装产品目录项；
   - **Image（镜像）**：二进制磁盘资产——发行版侧为装配输入（官方 rootfs tarball），实例侧为装配产物（根盘）；
   - **Instance（实例）**：产品的基础实体——用户创建的持久 Linux 环境（根盘 + 元数据：runtime 类别、实例状态等）；同一 Distro 可创建多个 Instance；
   - **Session（会话）**：用户与运行中 Instance 的一次交互/访问上下文（终端连接、期间的转发活动等）；随访问开始与结束，不持久。
3. 【产品决策·领域模型】MVP 单运行实例的准确表述是 **Session↔Instance 的配对约束**（任意时刻最多一个运行中 Instance → 最多一个活跃 Session），**不是实体合并**。未来多实例并发 = 放宽配对约束，实体模型与持久化结构不变。
4. 【工程假设·类比证据】单运行实例的资源现实性：QEMU 档每实例为持有 GB 级 RSS 的 VMM 进程；Podroid 按设备内存封顶 VM 内存配置（DeviceResourcePolicy）为旁证——在 RAM≥3GB 地板（ADR-0004）设备上多实例并存不可行。
5. 【待验证】AVF 档多 VM 并发的可行性与内存行为（并入原型票「AVF 端到端验证」观察清单）；多实例解锁的内存/功耗阈值（待「QEMU TCG 实机基线」原型与真实用户数据）。

## Considered Options

- **MVP 支持多实例并发（否决）**：内存翻倍与地板决策冲突；AVF 行为未测；UI 与冷恢复语义复杂化——收益不抵风险。
- **MVP 只允许存在一个实例（否决）**：多发行版试用（本产品核心卖点之一）需要多已停止实例并存。

## Consequences

- 实例管理的 UI 语义：实例列表（含状态）+ 单运行约束；"切换实例"是一等操作。
- 资源预算器 v1 只需处理"单运行实例"的预算问题；多实例预算器为后续增强。
- 冷恢复语义唯一：恢复那唯一的运行实例（ADR-0011）。
- "同时要两个发行版的服务"的答案指向 guest 内容器——与产品核心主张自洽。
