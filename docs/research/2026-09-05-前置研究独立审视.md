## 二、前置讨论逐条审视：哪些成立、哪些存疑

### 2.1 已被源码/官方文档证实（可信）

| 前置讨论的论断 | 核查结果 |
| --- | --- |
| Droidspaces 需要 Root | ✅ README 明确 "Root Required: Yes"，推荐 KernelSU，兼容 APatch/Magisk（Magisk/APatch 需 daemon 模式绕过 root-domain seccomp）；GrapheneOS 不支持 |
| Droidspaces 是特权容器、边界弱 | ✅ 原文："A Container is not a Jail"、"Droidspaces is not a sandbox for untrusted code"；GPL-3.0 |
| AVF 权限对第三方受限 | ✅ AOSP 源码实锤：`MANAGE_VIRTUAL_MACHINE` = `signature\|preinstalled\|development`（@SystemApi）；`USE_CUSTOM_VIRTUAL_MACHINE` = `signature\|development`，注释原文 "Not for use by third-party applications" |
| ADB 一次性授权可行 | ✅ `development` 保护级别正是 `adb shell pm grant` 可授予的原因；framework-virtualization README 明说 Android 14 起可 "for development purposes" 授权给其他 app。Podroid、koiTerminal 等同类项目均走此路径 |
| AVF Java API 并非公开 SDK API | ✅ AOSP main 分支 README：`android.system.virtualmachine` 全部为 `@SystemApi`（API 34 引入） |
| AVF 默认只能起 Microdroid 载荷 VM；自定义内核是另一条路径 | ✅ 公开形态：app 提供 payload（.so）跑在 Microdroid 上；自定义 kernel/initrd/os/bootloader 走 custom VM 配置（Android 16 出现 `VirtualMachineCustomConfig`），需要 `USE_CUSTOM_VIRTUAL_MACHINE` |
| 官方宿主↔VM 通道是 vsock | ✅ `vm.connectVsock(port)`；VM 只能监听、不能主动连 host；只有 owner app 能连接 |
| QEMU TCG 无法"接近原生" | ✅ Linaro 官方博客：aarch64 guest 约慢 8–12 倍；社区共识 5–20 倍（视负载）。**"0% 性能损耗"必须从产品语言中删除** |
| AVF 设备覆盖碎片化 | ✅ AVF 仅 ARM64；Pixel 6 起全系支持；三星直到 2026 年才在 Exynos S26 系列开启（Snapdragon S25 被主动禁用）；Snapdragon 8 Elite(Gen 5) 缺少 Terminal 所需的非保护 VM 支持；Google 自 Android 15/16 起对新 SoC 强制 AVF |
| Android 官方已亲自下场 | ✅ Android 16 内置 Terminal 应用 = AVF 上的完整 Debian VM，Pixel 10 已落地 GPU 加速（限制较多）。既是先例也是竞品 |
| Termux 类 W^X 限制 | ✅ targetSdk≥29 禁止从 app 可写目录 exec；Termux 锁死 targetSdk 28；Play 现要求 target 36；侧载最低 targetSdk 仍是 24（Android 15/16）→ 我们的 QEMU 等可执行文件必须以 jniLib 形式打进 APK（nativeLibraryDir 可执行），不能解压到 data 目录再执行 |
| Phantom process killer 仍在 | ✅ 32 个子进程的全局上限仍活跃，CPU 高占用子进程也会被杀；Android 14+ 开发者选项有官方关闭开关。QEMU 后端（app fork 子进程）受影响；AVF VM 由系统 VirtualizationService 托管，理论上不受影响（此半句为推断，待验证） |

### 2.2 前置讨论合理但未证实 / 需修正

1. **"Podroid 已完整实现 AVF backend + 9p over vsock + USB passthrough"** —— 讨论文档大量引用，但截至本报告仍在源码核查中（后台进行）。已确认的外围事实：rootless、Alpine VM + 自带内核、AVF 用 pKVM、QEMU 兜底到 Android 8+、需 adb grant；Release notes 提到 Pixel 8+ 上 AVF 后端单核（guest kernel 缺 CPU 频率驱动）、无 custom-VM API 的设备直接跑 pKVM。**在核查完成前，不应把 Podroid 的任何实现细节当作已证事实。**
2. **"PRoot 作为 Priority-3 正式后端"** —— 讨论文档把它写进架构图。我的独立判断：PRoot 与 VM 路线的领域模型完全不同（无 guest kernel、无真实 root、无 namespace/cgroup），塞进同一个 `VmEngine` 接口会造成抽象泄漏。**应作为独立决策工单讨论，默认倾向：MVP 不做，长期最多作为受限的 "utility 模式"**。
3. **"AVF 下 near-native"** —— 方向正确但需要 prototype 数据支撑（多核可用性、内存开销、I/O）。Podroid 在 Pixel 8+ 上单核运行的 release note 说明 AVF 路线自身也有坑。
4. **讨论文档对 app VM 的网络能力、GPU（gfxstream/virtio-gpu）可用性、VM instance 在 app 更新后的 identity/secret 行为**均未给出证据 —— 全部标记为"需研究/需原型"。
5. **讨论文档推荐 raw ext4 / sparse + squashfs + OverlayFS 的存储栈** —— 合理候选，但 Android app 私有存储（FUSE）上的镜像 I/O 特征、qcow2 支持情况需要 benchmark，不能拍板。

### 2.3 版本相关、随时可能变化

- AVF 权限字符串与保护级别（AOSP main，2026-09）
- `VirtualMachineCustomConfig`（Android 16 / API 36 新出现，演进中）
- Play targetSdk 政策（现为 36；侧载最低 24）
- 三星/OEM 的 AVF 开关状态（每年变化）
- Android 16 Terminal 的 GPU 加速范围（Pixel 10 先行）

## 三、当前理解（产品与领域模型）

**产品本质**：一个无 Root 的 Android Linux Runtime Platform。核心主张：

1. **VM-first**：每个 Linux 环境是带自己内核的完整 VM（硬件虚拟化优先，软件虚拟化兜底），容器能力（Podman/Docker/LXC、systemd、namespace/cgroup/OverlayFS）全部在 **guest 内部**解决，不依赖 Android host kernel——这是与 Droidspaces 的本质分界。
2. **Capability-driven backend selection**：`AVF 可用性`不是布尔值，而是一个能力谱（API 存在性 → MANAGE_VIRTUAL_MACHINE 授权 → custom-VM API → 非保护 VM → GPU/vsock/网络），能力检测与引擎选择必须是一等公民。
3. **Kernel/rootfs 解耦**：一个 guest kernel 契约 + 多发行版 rootfs，新增发行版 = 新增 rootfs 描述，不触碰 VM 层。
4. **性能承诺分层**（可测量、可验证）：
   - AVF/pKVM 档：near-native（以 benchmark 验收，不承诺 0%）
   - QEMU/TCG 档：compatibility-first（明确告知 5–20 倍 CPU 损耗的预期）
   - PRoot（若纳入）：最低门槛档，不承诺性能
5. **"无 Root"三级定义**（沿用讨论文档，予以确认）：L1 纯安装即用（仅 QEMU 路线可行）；L2 无 Root + 一次 ADB/Shizuku 授权（AVF 路线的现实前提）；L3 OEM/系统级合作（终局，非当前承诺）。

**MVP 画像**（我的独立建议，待 grilling 确认）：用户可从 UI 创建并启动一个 Alpine/Debian 实例并进入 shell（垂直切片穿过 UI→runtime→VM→guest→terminal），网络可用，文件共享/桥接最小化，GUI 仅软件渲染或完全不做。

## 四、最大的技术风险（排序）

1. **AVF 权限与政策风险（最高）**：near-native 卖点建立在 `development` 级权限的 adb 授权上，而 AOSP 明文 "Not for use by third-party applications"。Google 未来可能收紧，Play 上架基本无望走 AVF。→ 防御：QEMU 后端必须是一等公民而非摆设；密切跟踪 Android 16+ 的 `VirtualMachineCustomConfig` 演进；产品文案不把 AVF 当唯一卖点。
2. **设备碎片化**：AVF 可用 ≠ 体验一致（三星禁用、Snapdragon 缺非保护 VM、GPU 加速仅 Pixel 10、Podroid 在 Pixel 8+ 单核）。→ 防御：capability matrix + 每档能力的真实设备测试矩阵。
3. **QEMU 档体验预期**：5–20 倍 CPU 损耗意味着"发行版随便跑"的营销承诺会反噬。→ 防御：性能分层明示 + 默认推荐轻量发行版（Alpine）。
4. **Android 生命周期**：进程死亡、cached-app kill、phantom killer、OEM 后台查杀、Doze 对"长跑 VM"是持续威胁。→ 防御：前台服务策略 + VM 状态持久化 + 崩溃恢复为 MVP 必选项。
5. **范围失控**：GPU/USB/桌面/嵌套容器每个都是无底洞。→ 防御：wayfinder 决策票 + 垂直切片 + 明确非目标。
6. **许可证**：Podroid GPL-2.0、Droidspaces GPL-3.0、QEMU GPL-2.0、kernel GPL-2.0、crosvm（待核实，疑 BSD 系）。**"借鉴架构"与"复用代码"必须严格区分**，若复用 Podroid 代码则整个项目需 GPL-2.0 兼容。→ 防御：license audit 决策票。
7. **AVF VM instance 与 app 更新的纠缠**（研究项）：AVF 的 VM secret 派生自 payload/kernel 代码，app 更新可能使既有 VM instance 失效——对"发行版镜像随 app 分发"的模式有架构级影响，必须原型验证。

## 五、为什么应该使用 /wayfinder

- 问题空间是典型的 wayfinder 形态：**15+ 个相互牵制的产品/架构决策**，其中若干被研究和原型阻塞（AVF 实机能力、TCG 实测、网络模型、生命周期），远超单个 session；且用户明确要求"决策先行、禁止跳到实现"。
- 决策之间有依赖边（执行模型 → 后端契约 → 能力检测 → 发行版/存储/网络），需要可视化 frontier 让多 session 推进不迷路。
- 决策结论需要持久落盘（ADR/CONTEXT.md），跨 session 可追溯——wayfinder 的 decision ticket 天然提供。
