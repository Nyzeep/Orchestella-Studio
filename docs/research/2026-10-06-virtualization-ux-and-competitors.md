## 1. 执行摘要与战略背景

截至 2026 年 10 月，Orchestella Studio 已在 Android 平台上达成前三个阶段的技术突破（基线版本 `v0.3.0-alpha`）：
- **M1 底座**：打通了免 Root 双引擎虚拟化启动（QEMU 软模拟 L1 + AVF 硬件虚拟化 L2）、出站 NAT 网络、端口转发与只读共享；
- **M2 桌面**：废除了低效 VNC 软渲染，全面落地 Wayland-First 架构，交付了 60 FPS 满帧双缓冲显示、触控手势映射、虚拟按键栏及 Android IME 输入法穿透；
- **M3 互通**：交付了低延迟 PulseAudio/AudioTrack 流式音频、双向防环剪贴板、物理鼠标相对指针捕获及 SAF 文件拖拽暂存。

然而，站在工业级交付与真实终端用户体验的视角审视，当前产品仍暴露出显著的“工程师原型”痕迹：
1. **视觉体系简陋且割裂**：主界面（`activity_main.xml`）仍为极简的垂直列表与原生灰阶按钮堆叠，缺乏现代移动 OS（Android 15~17 / Material 3 Expressive）的动态色彩、沉浸式卡片和直观的状态呼吸动画；
2. **硬件参数不可定制（黑盒启动）**：vCPU 核心数、RAM 运存配额、磁盘容量被硬编码在代码常量中；用户无法根据物理设备性能（如 16GB 大运存平板 vs 6GB 紧凑手机）调整资源，无法防范 OOM 崩溃；
3. **实例生命周期缺损（缺少物理删除与存储回收）**：实例列表仅支持创建与启动，不支持对损坏或废弃实例的物理销毁，导致宿主私有目录中数 GB 的 `.raw` 磁盘镜像永久沉淀，形成不可逆的存储泄漏；
4. **下载引擎脆弱易断**：依赖单一官方源下载 rootfs tarball，无断点续传（HTTP Range），面对国内复杂的弱网或跨国网络波动时，下载频繁失败且每次必须从零重下数十至数百兆文件；
5. **终端交互简陋**：`TerminalActivity` 仍为纯文本 `TextView` 追加模式，缺乏 ANSI/VT100 256 色/真彩色解析，无语法高亮，辅助按键缺失，无法满足高阶开发者的命令行审美与生产力诉求；
6. **新手门槛高陡**：缺少环境授权、AVF 解锁与初次启动引导向导，导致非专业用户在面对“无 Root”、“虚拟化授权”、“Alpine vs Debian”等概念时极易流失。

本报告对标国内外 7 款标杆产品（Podroid、droidspaces、VMware Workstation、UTM iOS、Proxmox VE、Termux/Termux:X11、PojavLauncher），系统提炼其优秀功能哲学，在坚守 Orchestella Studio 独立技术路线（VM-first、免 Root、契约中立、Class A 资产绝对保护）的前提下，输出 M4 体验升级与全栈规格制定的完整依据。

### 2.1 Podroid / droidspaces（移动虚拟化对标）

#### 1. Podroid 体验与架构特征
- **UI 布局与实例组织**：采用 Jetpack Compose 编写 Material 3 界面。主界面展示单一运行状态卡片，包含启动/停止按钮、当前启动阶段文本（`bootStage`）与控制台输出流；
- **配置面板**：提供基础的端口转发编辑列表和运行模式切换（AVF vs QEMU），但核心资源（vCPU 核心数、RAM 分配、磁盘大小）为固定硬编码，无法在启动前或关机时调整；
- **rootfs 分发痛点**：
  * 将 Alpine Linux 镜像与内核以静态 Asset 随 APK 打包分发，导致初始 APK 体积臃肿；
  * 外部扩展包下载采用系统原生 `DownloadManager` 或裸 `HttpURLConnection`，没有任何分片下载、断点续传（HTTP Range）与镜像源加速策略；
  * 国内弱网环境下频繁发生 `java.net.SocketTimeoutException`，且每次重试均重头开始，导致大量用户卡死在首次解压阶段；
- **生命周期缺损**：只支持创建单一实例，无多实例列表管理，无“删除实例”与私有目录存储回收机制，卸载 App 是唯一清理存储的方式。

#### 2. droidspaces 机制反思
- 依赖 Linux namespaces、chroot/proot 机制运行用户态容器；
- 界面处于极早期阶段，操作高度依赖命令行，缺乏移动端卡片式生命周期管理；
- 在 Android 15/16 严苛的 SECCOMP 系统调用拦截下，系统调用频繁触发 Crash，不具备工业级长期演进可行性。

### 2.2 VMware Workstation / UTM iOS / Proxmox VE（桌面虚拟化哲学对标）

#### 1. VMware Workstation 的硬件定制哲学（"Hardware Customization"）
- **vCPU 拓扑规划**：允许用户选择虚拟处理器总数（Number of Processors）与每处理器核心数（Number of Cores per Processor），并提示不得超出宿主逻辑线程总数；
- **弹性 RAM 划拨与安全滑块**：
  * 直观展示物理机最大运存、推荐给虚拟机的最大运存（保留足够内存维持宿主 OS 流畅运行）、推荐配置与最低启动内存；
  * 采用绿-黄-红三色分段滑块，阻止用户将 RAM 拉升至可能导致宿主蓝屏或 OOM 的危险区间；
- **存储动态扩容（Sparse Disk Resizing）**：
  * 支持创建稀疏磁盘（Sparse/Growable Disk），仅占用实际写入大小；
  * 允许在虚拟机关机状态下安全扩容最大容量，磁盘文件头更新元数据，Guest 内部通过 `resize2fs` 自动接管扩容空间；
- **外设开关组件化**：网络适配器（NAT/桥接/仅主机）、显示卡（3D 加速开关、显存大小）、声卡、USB 控制器均具备独立勾选开关。

#### 2. UTM (iOS / macOS) 的移动卡片交互美学
- **卡片式管理（VM Cards）**：每个虚拟机呈现为一个圆角悬浮卡片，清晰展示：
  * 系统图标与名称（Debian / Alpine / Ubuntu）；
  * 实时状态指示微标（绿色运行中、灰色已关机、黄色挂起/恢复中）；
  * 资源摘要标签（如 `2 Cores · 2048 MB · 10 GB`）；
- **操作层级清晰**：
  * 单击直接拉起默认控制台（终端或图形桌面）；
  * 长按或点击上下文菜单弹出：编辑配置（Edit Configuration）、克隆（Clone）、共享/导出（Share/Export）、删除（Delete）；
  * **删除安全守卫**：运行中状态下禁止删除，按钮呈置灰状态；删除时弹出警示确认弹窗，明确提示“将彻底销毁该虚拟机的所有虚拟磁盘及数据”。

#### 3. Proxmox VE 的生命周期安全熔断
- **状态机绝对互斥**：在对虚拟机执行高危物理操作（销毁存储、缩减硬件、修改引导盘）前，底层强制检查 VM 状态；若状态为 `RUNNING` 或 `LOCKED`，物理 I/O 操作直接在内核层被拦截并拒绝；
- **级联存储回收（Cascade Storage Purge）**：删除操作自动绑定关联的所有物理卷、快照文件及元数据配置，杜绝孤立文件（Orphan Disks）滞留在存储池中。

### 2.3 Termux / Termux:X11 / PojavLauncher（终端与游戏容器对标）

#### 1. Termux 的终端交互与键鼠设计
- **移动专属辅助键盘栏（Extra Keys Bar）**：
  * 手机软键盘缺少 PC 标准按键，Termux 在键盘上方常驻一排高频辅助键：`ESC`、`TAB`、`CTRL`、`ALT`、`-`、`/`、`|`、`UP`、`DOWN`、`LEFT`、`RIGHT`；
  * 支持组合键锁定（按一下 Ctrl 变激活状态，紧接着按 C 发送 `SIGINT`）；
- **终端视觉渲染**：
  * 内置 ANSI 256 色与 24-bit TrueColor 真彩色解析引擎；
  * 预设现代等宽字体（JetBrains Mono、Fira Code）与配色方案（Monokai、Solarized Dark、Dracula），告别刺眼的黑白纯文本；
- **国内镜像换源（`termux-change-repo`）**：
  * 官方提供 `termux-change-repo` 交互脚本，允许用户在遭遇 GitHub/主服务器网络阻断时，一键切换至清华大学（TUNA）、中科大（USTC）、南京大学等国内知名开源镜像源；显著提升包管理与资源下载成功率。

#### 2. PojavLauncher 的分片断点下载引擎
- 移动端下载大型游戏运行环境（几百 MB 到上 GB）时，采用多线程分片下载与 HTTP `Range` 头断点续传；
- 本地记录已下载字节游标与分块校验和，网络波动中断后重新连接自动向后追加写入，拒绝从零重下；
- 具备自动故障转移机制：首选主源连接超时后，自动平滑切换至备用 CDN 镜像源。

## 4. Orchestella Studio 独立技术路线与设计哲学

在汲取竞品长处的同时，Orchestella Studio 必须保持自身的战略清醒，严格遵循以下四大独立设计哲学：

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                        Orchestella Studio 四大独立设计哲学                             │
└────────────────────────────────────────────────────────────────────────────────────────┘

 1. 【VM-First 独立内核路线】
    坚持 QEMU/AVF 完整虚拟机架构，坚决不向 PRoot 用户态劫持方案妥协，确保 Docker/Podman
    cgroups v2、独立网络栈及不受 SECCOMP 限制的完整 Linux 语义。

 2. 【策略中立契约设计（Strategy-Neutral Contracts）】
    无论是硬件定制（VmHardwareConfig）、音频流、剪贴板、还是终端与图形通道，所有功能
    定义在 `:runtime:contract` 中，执行策略（QEMU vs AVF）仅为运行时适配器，不侵入核心。

 3. 【Class A 资产绝对保护与合规纯净】
    坚守 ADR-0014，零代码复制任何 GPL 竞品实现（Podroid、Termux 等）；
    宿主 App 保持纯粹的 Apache-2.0 许可证，自研核心组件，第三方工具仅通过松耦合进程与网络桥接隔离。

 4. 【宿主优先的移动安全与防御纵深】
    虚拟机的激进配置决不能击垮 Android 宿主系统！
    建立物理运存嗅探防御（防 LMK）、删除熔断守卫（防误删与文件锁死）、EGL 鲁棒性隔离（防 GPU Crash）。
```

### 4.1 哲学一：VM-First 独立内核路线
绝不因为 PRoot 初始下载体积小或启动快而退回 PRoot 方案。随着 Android 15/16 对进程安全管控的收紧，PRoot 在现代 Android 系统上已陷入绝境。保持独立 Linux 内核，是提供真正可靠容器支持（Podman/Docker）和系统级完整性的唯一正道。

### 4.2 哲学二：契约中立与双执行引擎无缝演进
吸取 Podroid “后端非对称导致 Bug 频发”的教训，Orchestella Studio 的硬件参数模型（`VmHardwareConfig`）、生命周期持久化（`InstanceLifecycle.Store`）、以及呈现管道，完全建立在策略中立接口之上。QEMU 软模拟与 AVF 硬件虚拟化均实现同一套契约，业务层感知不到后端差异。

### 4.3 哲学三：宿主安全的防御纵深
移动设备不是服务器，宿主 Android 的稳定性高于一切：
- **内存安全**：禁止用户将 RAM 配置拉满至物理机规格，必须保留至少 2GB 物理内存供给 Android 系统；
- **存储安全**：实例删除必须在 `STOPPED` 或 `CRASHED` 状态下执行，防止向正在进行读写操作的磁盘镜像直接发起物理删除导致底层文件系统句柄破坏或宿主 I/O 挂起；
- **GPU 安全**：采用 EGL Robustness 上下文隔离，即便 Guest 3D 着色器进入死循环，也仅在沙盒内重置 EGL，杜绝引起手机死机重启。

## 5. 调研结论与转化建议

1. **视觉与交互升级不可拖延**：将原始的 `activity_main.xml` 全面替换为符合 Material 3 Expressive 规范的现代仪表盘，以 UTM 式的高质感卡片组织实例；
2. **硬件配置能力显性化**：引入 `VmHardwareConfig` 实体，为用户提供 VMware 式的核心、内存、磁盘与 GPU 自定义面板，并辅以安全的宿主硬件检测滑块；
3. **闭环实例生命周期**：在 `InstanceLifecycle.Store` 中实现物理删除接口与熔断保护，彻底解决存储泄漏；
4. **攻破网络阻断瓶颈**：构建支持多镜像源平滑 Failover 和 HTTP `Range` 断点续传的弹性下载引擎，彻底终结 rootfs 下载失败的用户痛点；
5. **升级终端体验**：改造 `TerminalActivity`，集成 ANSI 256 色解析与移动辅助按键栏，并在 `guest-assets` 中部署 Starship 现代化提示符；
6. **降低新手认知门槛**：交付 Setup Wizard 首次启动三步向导，重构输出分层清晰的《快速入门指南》与《高级调优与架构白皮书》；
7. **推进技术规格与工单落地**：将本报告调研成果与 GPU 加速报告融合，全面编制 `.scratch/orchestella-platform/spec-m4.md`，并在 `.scratch/orchestella-platform/issues/` 中拆解双轨拓扑示踪箭工单（Ticket 49 ~ Ticket 58）。
