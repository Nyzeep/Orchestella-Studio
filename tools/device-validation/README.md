# Host preparation for distro smoke

`PrepareDistroSmokeInputs.java` prepares offline inputs through the production Java APIs. It does not run a guest binary, Gradle, Android, a device, or a network client. All four arguments are mandatory. Supported IDs come from `DistroCatalogRegistry`: `ubuntu,debian,fedora,arch,opensuse,almalinux,rocky`.

Compile with the existing JDK and cached build classes, without downloading anything. Example PowerShell (run from the repository root; choose a new external build directory):

```powershell
$smoke = 'D:/Development project(开发项目)/Orchestella开发目录/Orchestella/artifacts/quality-20261013/device-smoke'
$build = "$smoke/prep-tool-build"
New-Item -ItemType Directory -Path $build -ErrorAction Stop
$deps = 'W:/app/build/intermediates/javac/debug/compileDebugJavaWithJavac/classes;W:/runtime/contract/build/libs/contract.jar;W:/runtime/distro/build/libs/distro.jar;W:/runtime/instance/build/libs/instance.jar;W:/runtime/engine-qemu/build/libs/engine-qemu.jar'
$app = 'app/src/main/java/io/github/nyzeep/orchestella'
& D:/JDK17/bin/javac.exe -encoding UTF-8 -cp $deps -d $build tools/device-validation/PrepareDistroSmokeInputs.java "$app/DistroInstanceCreator.java" "$app/QemuRuntimeBootstrapper.java" "$app/GuestRuntimeProvisioner.java" "$app/DistroMirrorProvisioner.java" "$app/FirstBootProvisionPipeline.java"
if ($LASTEXITCODE -ne 0) { throw 'javac failed' }
$batch = "$smoke/final-apk-batch"
New-Item -ItemType Directory -Path $batch -ErrorAction Stop
& D:/JDK17/bin/java.exe -Xmx512m -cp "$build;$deps" PrepareDistroSmokeInputs --apk 'W:/app/build/outputs/apk/debug/app-debug.apk' --inputs 'D:/Development project(开发项目)/Orchestella开发目录/Orchestella/artifacts/quality-20261013/distro-inputs' --output $batch --distros 'ubuntu,debian,fedora,arch,opensuse,almalinux,rocky'
if ($LASTEXITCODE -ne 0) { throw 'preparation failed; discard this partial batch after inspection' }
```

Choose the actual final APK explicitly. Output must be an existing directory within the date-specific external `device-smoke` root. Existing selected distro directories, `private`, `hostSparse`, or `plan.json` are refused. Failed batches have no published plan and are never resumed or overwritten. Compile the five current app source files above to avoid stale cached app bytecode; the four cached runtime jars must match the final build. No `android.jar` is needed for this preparation path.

`plan.json` is the ready signal and contains `schemaVersion`, APK hash/size, packaged entry hash/size, `privateCredentials`, and `instances`. Each instance records `distro`, `version`, `instanceId`, `relativePhoneDir` (`files/quality-smoke/<distro>-<shortid>`), hardware (2 vCPU / 1024 MB / headless for six smaller inputs; Arch 3072 MB), `memoryMinimumMegabytes`, `exclusiveScheduling` (Arch only), `baselineMandatory: true`, `mirrorSource: OFFICIAL`, `autoUpdate: false`, `rawBytes: 8589934592`, and the production creation `marker`. Runtime fields `kernel`, `initramfs`, and `baseInitramfs` contain output-relative `path`, `bytes`, and `sha256`; the first two files are `<id>/runtime/Image` and `<id>/runtime/initramfs-embedded.cpio.gz`. Control/terminal socket names and gateway IDs are independent; `gatewayPort: 0` means the driver allocates a distinct ephemeral listener for each gvproxy/NAT instance.

`private/credentials.json` has `schemaVersion` and `instances`, whose fields are `distro`, `instanceId`, `bridgeToken`, `guestPassword`, `username`, and `hostname`. Production FileStore metadata is also under `private/<id>/instances`. These files and the credential-bearing embedded initramfs are owner-only (0600/0700 on POSIX, verified owner-only ACL on Windows). Never print their contents, include them in reports/Git, or upload them. Retain synthetic QA credentials until acceptance; the main session owns cleanup.

`hostSparse/<id>/root-volumes/<uuid>.raw` only satisfies the bootstrap API. Do not push it. The production creator first creates a new verified 4096-byte marker seed; the tool retains it as `.creator-marker` and creates the same raw pathname with `CREATE_NEW + SPARSE`, extending to 8 GiB. This avoids allocating 8 GiB on Windows because the existing creator does not request the SPARSE flag. On the phone the main driver must create a fresh isolated directory and `root-volume.raw` exclusively (O_EXCL / no clobber), write the plan's exact ASCII marker, and truncate to `rawBytes`. Existing files must always fail. Push only the runtime kernel and embedded initramfs; use the final APK's existing native runtime for launch.

The APK's strict runtime manifest verifies all seven required runtime artifacts. `Image` is read from `assets/Image`; initramfs, `guest_init`, and `proxy_relay` are read from APK-root resources. Guest profile/provision/agent content is preserved from that APK. Rootfs inputs are read-only and verified against the trusted catalog by both creation and embedding. This host utility creates separate QA stores and does not alter the App's single running instance model.

## Finite phone smoke driver (main session only)

`run_distro_smoke.py` uses only Python's standard library and an existing adb. The worker that authored it does not operate the device. The main session first stops its current App VM, then supplies its serial and the installed APK's native directory, established through its own `pm dump` inspection. Example PowerShell, after preparing a new batch from the frozen actual APK:

```powershell
$smoke = 'D:/Development project(开发项目)/Orchestella开发目录/Orchestella/artifacts/quality-20261013/device-smoke'
$apk = "$smoke/verified-baseline-apk.apk"
$hash = (Get-FileHash -Algorithm SHA256 $apk).Hash.ToLowerInvariant()
python tools/device-validation/run_distro_smoke.py --plan "$smoke/final-baseline-batch/plan.json" --apk $apk --apk-sha256 $hash --serial '<main-device-serial>' --native-dir '<installed-native-directory>/lib/arm64' --output $smoke --distros 'debian,fedora' --parallel 2 --timeout 3600
```

`--apk-sha256` is mandatory and must match both the actual APK and public plan. The driver checks strict APK runtime manifest, all prepared artifact hashes/sizes, private/public instance identity, phone path/socket scope, credential separation, and memory metadata before adb work. Phone-side native QEMU/gvproxy and copied kernel/initramfs hashes must also match that APK/plan. No host root raw is pushed. The driver rejects an existing phone distro directory/raw and retains new phone raw/logs for diagnosis.

Each guest gets its own legacy gvproxy listener/NAT and abstract terminal/control/proxy sockets. YAML uses the current `NetworkGatewayDaemon.configuration()` stack fields, empty `forwards`, and omits `services` as requested for this QA path. There are no LAN listeners or forwarding API calls. Gateway readiness requires its owned process and actual waiting-for-clients log, with the listener table as an optional fallback. Android `/proc/net` denial is recorded as `networkTableAvailable: false` and a sanitized command diagnostic; it does not stop launch. Actual bind errors or process exit fail at the gateway stage. It never opens the single-client gateway listener as a probe. `--port-base` defaults to 24000, with one distinct port per selected guest; an already bound port is refused.

The driver creates a unique `/data/local/tmp/quality-smoke-qa-run-<id>-<distro>` staging directory for explicit kernel/initramfs/launch files. After run-as copies and verifies the payload into fresh owner-only app storage, staged kernel/initramfs are immediately removed. Cleanup removes only that staging directory's three named files, its own adb forwards, and processes whose PID/start-time/command line match the new QA directory. No app-private disk or directory is deleted. `nohup` output is isolated in per-guest `.stdout.log.txt` files, and PID metadata is explicit. Gateway YAML is written with quoted `printf` plus noclobber; no Android heredoc temporary file is needed.

Initial HELLO retries back off through 1, 2, 4, 8 and 15 seconds (15-second cap), with a `--startup-timeout` budget of 3900 seconds, always capped by the per-guest overall `--timeout`. The same read/write pump reads replies between retries. Only this initial handshake tracks each partial send's exact byte offset, tolerates temporary write pressure for at most 10 seconds per frame, and finishes a partly written repeat before returning an acknowledgment. `initial-hello-write-timeout` is a HELLO transport/setup failure, not a distro baseline verdict. Results expose only safe counters `initialHelloFrameCount` and `initialHelloWriteWaits`. The reduced retry rate accommodates verified large rootfs hashing and bounded unpacking without flooding a not-yet-running guest agent. Normal RESIZE/POWER waits remain 15 seconds. Duplicate READY messages cannot acknowledge RESIZE or POWER. An ADB local TCP accept alone does not prove that the remote QEMU abstract socket is bound. During the first HELLO only, an immediate EOF/reset may reconnect within 30 seconds if no control response bytes and no terminal bytes have been observed. Each retry closes its sockets and joins the old sole terminal reader before reconnecting to the same owned forwards; the same terminal log is appended. Partial control replies, any terminal output, and failures after authentication are not retried. Results record `initialChannelAttempts`, `initialChannelReadiness`, and `initialHelloAcknowledged`; exhausted setup reports `initial-channels-not-ready` at the HELLO stage. This does not probe gvproxy's single-client listener. The terminal is continuously read with an incremental UTF-8 decoder, without writes until an actual shell prompt (`❯`, `#`, `$`, or OSC133 B) and explicit baseline-ready state are observed. Expected recovery bootstrap is allowed. Explicit failed/action-required provisioning or a kernel panic fails. CSI/OSC sequences are removed for probe parsing. One nonce probe checks native PID1, cgroup2, DBus/SSH service activity, package manager, official host DNS, exclusive QA root write plus sync, and the persistent ready state. Every check and the complete begin/end marker block must pass; echoed command text does not count. Successful probes reauthenticate HELLO on the same control connection (one-second retries, at most 60 seconds) because native handoff can restart the agent and discard the recovery session's authentication. They then request controlled poweroff and verify QEMU exits. Known bridge errors retain a fixed public reason, such as `control-rejected-unauthorized` or `control-rejected-malformed-command`; unrecognized response payloads remain hidden.

`--timeout` defaults to 1800 seconds per guest (3600 is available); `--parallel` defaults to 2, limited to 1 or 2. Arch always runs alone and has explicit 3072 MB in the plan because its 829 MB embedded rootfs needs room for both initrd and extracted input. The minimum is `max(1024, ceil(2 * initramfsBytes / MiB) + 512)`; an under-sized plan is refused rather than silently overridden. Results go into a new `qa-run-<id>` directory under the existing `--output` root. Public JSON and terminal/native log tails are sanitized. Failed adb commands retain their label, exit code, elapsed time, and last 8192 bytes of sanitized stdout/stderr in `commands[].diagnostic`, while host credentials remain read-only in their private JSON. Guest DNS/package work is confined to its ordinary outbound NAT. Device behavior remains for the main session to validate.

For the next driver process, fixed readonly progress sampling defaults to `--progress-interval 60`. Set it to `0` to disable automatic sampling. A manual request is an empty regular file at `<qa-run>/<distro>/progress.request`; its contents are never read or executed. The driver sends only the fixed `QA_PROGRESS_DIAG` command: PID1 name, provisioning state, and the last 20 lines of `/var/log/orchestella-provision.log.txt`. It uses the existing terminal connection during HELLO/baseline waits and requires an OSC133 B prompt observed within the last 60 seconds, with no subsequent OSC133 C. Without an available prompt the request stays pending. Baseline-ready or the guest deadline stops new diagnostics.

Processed requests are atomically renamed to unique `progress.request.<sequence>.<uuid>.processed` receipts. Each sample is preserved separately in `progress-0001.json`, etc., with source, timing, status and sanitized output; `terminal.log.txt` also retains the sanitized stream. Results mark `readonlyProgressUsed` and list `progressSamples`. A diagnostic that does not complete within 15 seconds records a timeout without declaring provisioning failed. The full smoke probe waits for the pending diagnostic and a fresh prompt; its seven checks and nonce success markers remain independent. No second terminal client or reader is created. Existing running processes do not reload this change.

When baseline explicitly fails, the driver collects one final fixed diagnostic before cleanup, writes `failure-progress.json`, and records `failureProgress` in the failed result. It waits at most 15 seconds, capped by the overall deadline. An old but unconsumed complete OSC133 B is eligible even beyond 60 seconds; subsequent C, a consumed/incomplete prompt, or a visible input request blocks sending. A pending fixed diagnostic is completed rather than overlapped. Missing end markers record a timeout and never count as success. NUL bytes are removed only from the display/parser view; the sanitized original terminal stream is retained in `terminal.log.txt`. The failure outcome and seven-check success criteria remain unchanged.

## Explicit failed-QA resume

Use this only for a failed QA instance that the driver created. Keep the original plan, its private credentials/FileStore metadata, runtime files, and the per-distro failed `result.json` plus host `launch.sh`. The original run's aggregate `results.json` is optional while other guests are still running. A successful result, a never-started QEMU, unknown identity, changed credentials, or unverified current original-PID state is refused. A historical `cleanupError` remains intact in the original result and is carried into new audit fields `historicalCleanupError` and `requiresCurrentCleanupVerification: true`; it does not replace the mandatory phone-side stopped-PID verification. Only a successful resume preparation sets `currentCleanupVerified: true`.

After freezing the corrected actual APK, recompile the preparation tool and rebootstrap into a new empty output root with the original plan:

```powershell
& D:/JDK17/bin/java.exe -Xmx512m -cp "$build;$deps" PrepareDistroSmokeInputs --apk $apk --inputs 'D:/Development project(开发项目)/Orchestella开发目录/Orchestella/artifacts/quality-20261013/distro-inputs' --output "$smoke/resume-inputs" --distros 'almalinux,opensuse' --resume-plan "$smoke/original-batch/plan.json"
python tools/device-validation/run_distro_smoke.py --plan "$smoke/resume-inputs/plan.json" --apk $apk --apk-sha256 $hash --resume-plan "$smoke/original-batch/plan.json" --resume-results "$smoke/qa-run-<original-id>" --serial '<main-device-serial>' --native-dir '<installed-native-directory>/lib/arm64' --output $smoke --distros 'almalinux,opensuse' --parallel 2 --port-base 24470 --timeout 3600
```

`--resume-plan` on Java loads and cross-checks original plan/credentials against the original production FileStore instance, then calls the existing bootstrap API with the same UUID, credentials, hardware and original host sparse path. It does not call the creator or write the old raw/metadata. New public plan fields `resumeFromPlanSha256` and `resumeFromApkSha256` link the explicit old source. Each resumed row also records `hostSparseSourcePlan` (`path` relative to the approved `device-smoke` root and `sha256`), pointing to the original fresh QA plan. `hostSparseRoot` remains relative to that original plan's batch; `hostSparseRootBase: resume-source-plan` identifies this reference. Repeated resume works even when the immediately preceding plan has no sparse raw of its own. The tool resolves the original FileStore raw only inside the approved root and the exact `hostSparse/<distro>/root-volumes/<uuid>.raw` layout, then cross-checks the original fresh plan, original instance/credentials/hardware, 8 GiB size, creation marker and retained `.creator-marker` seed. An existing provenance pointer must match; legacy resumed plans without it are accepted only after these original-source checks. No arbitrary approved-root file becomes a raw input. The new batch's private metadata and credentials are owner-only.

Python requires both `--resume-plan` and `--resume-results`. It checks old/new identity, unchanged credentials, original plan link and retained failed result. The source must remain within the approved external root. Before replacing phone runtime files, it verifies the phone's original launch SHA against the original host launch file, original kernel/initramfs hashes against the old plan, the new staged payload/native hashes against the new APK, and no symlinks. The original raw must remain 8 GiB and have the ext4 superblock magic; both old PID/start-time records must no longer identify a live process. Unreadable live-process metadata fails closed.

Only eight named runtime/config/PID/log files move into a new `previous-run-<uuid>` archive under that same QA phone directory. New runtime files are published without replacing an existing file. The raw is never written, moved, marked, formatted or truncated by the resume shell; its inode and size are checked before and after staging. The guest must emit `DROIDLAYER_ROOT_VOLUME_RESTART version=1` and must not enter root assembly format/unpack. Full baseline and all seven probe checks plus controlled poweroff are still required. New results record original-result hash, previous-file archive name, `rootRawPreserved`, `rootRestartObserved`, and APK/plan/launch hashes. Device filesystem preservation remains for the main session to validate; the worker's resume checks use host fixtures and simulated channels only.

If Arch was interrupted during assembly rather than package provisioning, add explicit `--resume-assembly` with `--distros arch` and both resume source arguments. The old/new catalog rootfs hashes must still match. In this mode the driver requires the guest's exact `DROIDLAYER_ROOT_VOLUME_RESUME phase=assembly preserving-filesystem` marker before permitting unpack; the existing guest verifies its persisted assembly marker against the trusted rootfs hash. Formatting is always rejected, and all baseline/probe checks remain required. This option is refused for other distros or mixed batches. The default resume mode continues to require a completed-root restart and refuses reassembly.

For owner inspection of a failed openSUSE cold boot, add `--recovery-diagnostics --distros opensuse` to the explicit resume command. Both original source arguments and all APK/instance/credential/phone SHA/ext4/PID ownership gates remain mandatory. Mixed batches, implicit distro selection, fresh mode, and `--resume-assembly` are refused. Prepare the same-instance inputs from the corrected frozen APK containing the explicit guest recovery branch first; this driver flag only appends `orchestella.recovery=1` to QEMU's kernel command line.

After authenticated HELLO and RESIZE, this mode waits up to 60 seconds for an unconsumed complete OSC133 B prompt (and a preserved-root restart marker), then sends exactly one fixed readonly command: PID1 name, provisioning state, the last 40 package log lines, `journalctl --no-pager -b -1 -n60`, and `/etc/fstab`. It accepts no command text, never sends the seven-check root-write probe, and does not infer readiness from a recovery shell. Complete `QA_RECOVERY_DIAG`/`QA_RECOVERY_DIAG_END` output is required within 60 seconds, capped by the guest overall deadline; the sanitized output is saved to `recovery-diagnostics.json`. Normal progress IPC is disabled in this mode to prevent competing commands.

Per-instance and summary results explicitly record `diagnosticOnly: true`, `baselinePassed: false`, `diagnosticsCollected`, and always `passed: false`. After collection the normal re-HELLO and controlled POWER acknowledgment/exit checks run, followed by owned cleanup. Per-instance `diagnosticOperationSucceeded` and summary `operationSucceeded` describe only that operation. Exit code 0 means collection and shutdown/cleanup succeeded; it does not mean openSUSE passed baseline validation. Missing prompt/end markers, failed HELLO/POWER acknowledgments, or cleanup failures produce exit code 1. The main session owns device execution; this mode was verified by the worker with host-only simulated channels.

To explicitly retry baseline installation on that preserved openSUSE QA root, add `--recovery-retry` alongside `--recovery-diagnostics --distros opensuse` and both resume source arguments. Without the new flag recovery diagnostics remain readonly. The retry sends one fixed foreground `orchestella-guest-provision --retry` call on the existing terminal, then serially records its exit code, a separately delimited final state, the last 40 package log lines, previous-boot journal and fstab. It accepts no external command text and does not recreate or re-extract the root. This authorized operation can install packages through the guest's ordinary network path and retain its cache.

Retry collection uses the remaining overall `--timeout` (up to 7200 seconds), rather than the readonly collector's 60-second bound. A matching zero command/end return code and final persisted `status=awaiting-init` or `status=ready` are required for `retryCheckpointReached: true`; historical ready lines in package logs do not count. Package failure still saves complete terminal output and `recovery-diagnostics.json` before controlled POWER/owned cleanup. Results add `ownerOperation: baseline-retry`, `retryExitCode`, `retryState`, and `retryCheckpointReached`. They retain `diagnosticOnly: true`, `baselinePassed: false`, `distroPassed: false`, and `passed: false`; awaiting-init confirms a package checkpoint, not native services readiness. `operationSucceeded`/exit 0 require that checkpoint, complete collection and successful controlled shutdown/cleanup. Failed packages, missing end markers or shutdown errors leave the operation failed.

An earlier completed openSUSE diagnostic result can be an explicit resume source even without `failedStage`, provided it is diagnostic-only, baseline-not-passed, has collected diagnostics and a successful controlled diagnostic operation, retains the raw, and contains matching APK/plan/launch hashes. The original identity/credentials/runtime/phone/PID ownership checks still run. A successful distro result, incomplete diagnostic, fabricated baseline pass or missing source hashes is refused. Use the most recent QA run and its matching plan so phone runtime hashes reflect the last attempt.
